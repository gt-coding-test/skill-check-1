## 設定ファイル

### ロードの例

課題1の入力例1・2を`SysctlConf.load`でロードしたときに、変数に格納される内容です（同じファイルが`src/test/resources/`にあり、テストで検証しています）。

#### 入力例1

入力（`example1.conf`）

```
endpoint = localhost:3000
debug = true
log.file = /var/log/console.log
```

出力（`conf.tree`）

```scala
Map(
  "endpoint" -> Leaf("localhost:3000"),
  "debug"    -> Leaf("true"),
  "log"      -> Node(Map(
    "file" -> Leaf("/var/log/console.log")
  ))
)
```

#### 入力例2

入力（`example2.conf`）

```
endpoint = localhost:3000
# debug = true
log.file = /var/log/console.log
log.name = default.log
```

出力（`conf.tree`）

```scala
Map(
  "endpoint" -> Leaf("localhost:3000"),
  "log"      -> Node(Map(
    "file" -> Leaf("/var/log/console.log"),
    "name" -> Leaf("default.log")
  ))
)
```

同じ入力に対する`conf.toMap`（階層化しない形）

```scala
Map(
  "endpoint" -> "localhost:3000",
  "log.file" -> "/var/log/console.log",
  "log.name" -> "default.log"
)
```

### 文法と仕様

sysctl.conf(5)に書かれているもの:

- 1行は`token = value`形式。`=`の前後の空白は任意
- 空行、および`#`か`;`で始まる行は無視
- 値に引用符は不要で、空白を含められる（`kernel.modprobe = /sbin/mod probe`）
- 行頭の`-`は「設定に失敗しても無視する」の意味。キーには含めず`Entry.ignoreErrors`として保持する

manページに無く、procpsのsysctl(8)の実装（`sysctl.c`）に合わせたもの:

| ケース | 挙動 |
| --- | --- |
| 行頭・行末の空白 | 取り除く（インデントされたコメントも無視）。空白の定義はCの`isspace`と同じASCIIの空白のみ |
| 値に含まれる`=` `#` `;` | 値の一部として扱う（最初の`=`で分割、行内コメントは無い） |
| `=`の無い`-key` | 「このキーには設定しない」という除外行。値が無いのでMapには入れず、`conf.exclusions`に保持する |
| `/`区切りのキー | `net/ipv4/ip_forward`は`net.ipv4.ip_forward`に正規化する。最初の区切りが`/`なら`/`と`.`を入れ替えるので、`net/ipv4/conf/eth0.100/rp_filter`の`eth0.100`は1つのセグメント（`eth0/100`）になる |
| 同じキーの重複 | 後勝ち。`entries`には全て残る |

このライブラリで決めたもの:

| ケース | 挙動 | 理由 |
| --- | --- | --- |
| `=`が無い行（除外行を除く） | `Syntax`エラーでロード全体を失敗させる | sysctl(8)は警告して続行するが、読み飛ばすと設定ミスに気付けない |
| キーが空、`--key`、キーに空白（`- key`を含む）、空セグメント（`a..b`） | `Syntax`エラー | manページの「single -」に従う。階層化したときに意味を持たないキーは受け付けない |
| キーに全角スペースなど非ASCIIの空白 | `Syntax`エラー | 前後の除去はASCIIの空白だけなので、行頭や`=`の直前の全角スペースがそのままキーに入ってしまう。値に含まれる分はそのまま残す |
| `log = a`と`log.file = b`の同居 | `KeyConflict`エラー | 1つのキーが値と階層の両方になり、Mapに格納できない |
| 値が空（`key =`） | 空文字列として格納 | 空の値を書けるようにしたい |
| 値の型 | すべて`String` | sysctl.confに型は無い。`true`や`3000`をどう解釈するかは使う側で決める |
| 順序 | 定義順を保持 | 出力やデバッグ時にファイルと対応が取りやすい |
| エラーの件数 | 最初の1件だけを返す | 文法が誤った行があると設定の内容を確定できず、以降の行のキーの衝突や後勝ちを正しく判定できない |

対象外:

- キーのglob（`net.ipv4.conf.*.rp_filter`）の展開。`*`はそのままセグメント名として格納する
- 除外行の適用。`conf.exclusions`に保持するだけで、`tree`や`toMap`からキーを取り除くことはしない
- 値の最大長4096文字（カーネルの/proc由来の制限）のチェック

## スキーマ

### スキーマファイルの書式

書式は[README](../README.md#スキーマファイルの書式)のとおりです。ここには、型が受け付ける値だけを載せます。

| 型 | 受け付ける値 |
| --- | --- |
| `string` | 任意の文字列（空文字列を含む） |
| `bool` | `true`または`false`（小文字のみ） |
| `integer` | 10進の整数。`-`は可、`+`は不可。64ビット符号付き整数に収まるもの（`3`、`-1`） |
| `float` | 10進の小数。整数も可（`0.5`、`-2`、`1.5e3`） |

### 検証の仕様

| ケース | 挙動 | 理由 |
| --- | --- | --- |
| 値が型として解釈できない | `TypeMismatch`（行番号、キー、期待する型、実際の値） | どの行をどう直せばよいかが分かるようにしたい |
| スキーマにあるキーが設定に無い | 型に`!`を付けたキーだけ`MissingKey`（キー、スキーマの行番号）。付けていないキーは省略可 | 課題のスキーマ例の`retry`は課題1の入力例に無く、スキーマに書いただけで必須になると例同士が通らない。必須にしたいキーは明示する |
| スキーマに無いキーが設定にある | `UnknownKey`（行番号、キー）。`schema.allowUnknownKeys`で許容できる | キーの書き間違い（`retrys = 3`）は、検証しないと見落とす。一部のキーだけを検証したい場合は許容もできる |
| 不備が複数ある | すべて返す。設定ファイルの行の順、続いて不足しているキーをスキーマの定義順 | 設定の内容が確定した後の検査なので、1件ずつ直して再実行する手間を省ける |
| 必須（`!`つき）のキーの値が空（`endpoint =`） | `string`なら通る。必須かどうかは、キーが設定にあることだけを見る | 値の中身は型の検査の範囲で、`string`は空文字列を受け付ける |
| 同じキーが複数ある | 後勝ちで有効になる値だけを検証 | Mapに格納される値と検証対象を一致させたい |
| 行頭に`-`の付いた設定 | 通常の設定と同じく検証 | 値を持つ設定であることは変わらない |
| 除外行（`-key`） | 検証しない | 値を持たない |
| 設定とスキーマで区切り文字が違う（`log/file`と`log.file`） | 正規化後のキーで照合するので一致する | 設定ファイルの文法と揃えたい |
| 検証後の値 | `String`のまま。`Boolean`や`Long`への変換はしない | スキーマの有無で格納形式を変えたくない |

### エラーを返す順序

1. スキーマファイルの不備（`InvalidSchema`）。最初の1件
2. 設定ファイルが読めない、または文法エラー（`Io` / `Syntax` / `KeyConflict`）。スキーマ無しの場合と同じで、最初の1件
3. 設定がスキーマに従っていない（`SchemaViolation`）。全件

### スキーマファイルの不備

次のものはスキーマファイルの不備として扱います。スキーマの誤記に気付かないまま検証が素通りしたり、設定の不備として報告されたりするのを防ぐためです。

| ケース | エラー |
| --- | --- |
| `->`が無い、型が無い、知らない型（`int`、`integer?`など） | `Syntax` |
| キーが空、空白を含む、空セグメントがある | `Syntax` |
| キーが`-`で始まる、`=`を含む | `Syntax`。設定ファイルの行頭の`-`や最初の`=`はキーの一部にならないので、一致する設定を書けない |
| 同じキーを2回定義 | `DuplicateKey` |
| 階層が衝突するキーの組（`log`と`log.file`） | `KeyConflict`。1つの設定で同時には持てない組なので、どちらかが誤記の可能性が高い。`!`の有無に関係なくエラーにする |

### 検証の対象外

- キーのglob。スキーマと設定のキーは完全一致で照合する
- 型の別名（`int`、`boolean`）や、`bool`としての`1`/`0`
- `->`を含むキー。設定ファイルには書けるが、スキーマでは`->`がキーと型の区切りになるので指定できない
- 値の範囲・列挙・正規表現などの制約
